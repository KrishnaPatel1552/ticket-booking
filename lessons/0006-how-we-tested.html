26 and 28. Real API, real Postgres

The tests call the same HTTP API a customer would call. They run against PostgreSQL, the database named ticket_booking_test. A mock of the database would not enforce one_active_event_seat. Then a test could pass while two people still get the same seat.

Say this

I test through the API on real Postgres, because the rule that stops a double sell lives in the database, not in a mock.

27 and 34. Two users, and the caps

Two customers at once: the test starts two threads, both try to hold or buy the last seat, and it expects one success and one conflict.

The caps: one customer asks for 7 seats and gets the order-limit error with nothing saved. A customer who already has tickets asks for more than the room left under 12 and gets the event-limit error. Two of their requests run together, and the second one finds the spots gone.

Say this

I race two customers at the last seat. I also ask for one seat too many, alone and at the same time, and I expect zero new holds.

29. Hold expiry without waiting

Tests do not sleep for 10 minutes. They move the clock with POST /api/test/clock. That endpoint exists only in the test profile. Production uses the real clock. After the clock jumps past the hold, opening the event releases a hold that has no payment.

Say this

I move a test clock past the hold, then open the event. I do not wait ten real minutes. That clock endpoint is not in production.

30. Positive, negative, boundary

  • Positive: a normal hold, a success checkout, a ticket on the order.
  • Negative: a second customer on a held seat, a decline, a request over the cap.
  • Boundary: the exact edges. Six seats is allowed. Seven is not. Exactly 48 hours is half. Under 48 is nothing. Exactly 168 is the full net. A hold at 9 minutes 59 seconds is still held. At 10 minutes, opening the event frees it.

Say this

Happy path, then the reject, then the exact edge: 6 versus 7, and 48 hours versus one second under.

31. Payment success, decline, timeout, unknown

The mock result is chosen by the caller. Each one has an expected end.

  • Success: payment succeeded, seat is a ticket, money taken once.
  • Decline: payment declined, no ticket, seat free.
  • Timeout and unknown: both store unknown. No ticket. Seat stays held. A later lookup of success writes the ticket. A lookup of decline frees the seat. Another timeout leaves it unknown.

Say this

I script all four results. Timeout and unknown are the same stored state. Only a lookup of success or decline finishes them.

32. A refund is not paid twice

The refund row is saved before the mock, and that refund is finished by lookup, not by calling the mock again. A failed refund is repaired with the same cents already stored, not a new calculation that could pay a different amount. Tests assert the status and the cents after success, decline, and a second lookup.

Say this

One refund row, one mock call, then lookup. A repair uses the cents already stored, so we cannot invent a second amount.

33. Unit, integration, end to end

Keep the words plain.

  • Unit: one small piece, no database. Example: how 100 cents splits into 34, 33, and 33.
  • Integration: the API plus Postgres. This is most of our tests. Two users, the caps, the clock.
  • End to end: a person in the browser. The site tests cover the map. They do not replace the Postgres tests.

Say this

Unit tests a pure split. Integration tests the API on Postgres. Browser tests check the screen. The double-sell proof is the integration test.

35. A test that fails sometimes

I would not rerun it and hope. I would ask what it shares with another test: the clock, the same seat, the same customer. A race often hides a missing lock or a clock that was not reset. I would run that one test alone, then with the neighbor that touches the same row, and read which request won.

Say this

I treat a flaky test as a race. I look for a shared seat, a shared clock, or a missing lock, and I run the two suspects together.
