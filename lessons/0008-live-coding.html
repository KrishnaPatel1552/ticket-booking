If he asks you to change it

Six practice edits. Say where the code already lives, what you would touch, and which rule must stay true.

Part 1 Part 2 Part 3 Part 4 Part 5 Part 6

Do not change the product while you practice. In the interview, change the smallest thing, then the test that would catch the old behavior.

Practice 1. Reject a hold over six seats

This already exists. HoldSeats computes room on the order and room at the event. The order cap is 6. If the request is bigger than the smaller room, it throws and writes nothing.

If he asks you to add it, show that check. Then show a test: 6 seats succeed, 7 seats save nothing.

Say this

The six-seat rule is already the order cap. A request past it writes zero holds. I would show the check and the seven-seat test.

Practice 2. Change a refund rule and its edge test

Open RefundBand. Suppose he says “half starts at 24 hours, not 48.” You change the 48. You do not touch the fee. Then you find the test that cancels at exactly 48 hours and move that edge to 24. The test at exactly 168 hours must still expect the full net.

Say this

I change the number in the band method and the test at that exact hour. I leave 168 and the fee alone unless he asked for those too.

Practice 3. Confirmed ticket count

There is already a count of active rows for a customer at an event. That count includes holds and tickets. A new endpoint must count tickets only, or you will report holds as confirmed tickets.

Shape: authenticated GET, that customer, that event, kind ticket, active. A test with 2 tickets and 1 hold must return 2.

Say this

I will not reuse the cap count. That one includes holds. Confirmed means tickets only.

Practice 4. Admin releases a blocked seat

This already exists as an API, not as a screen. An admin calls release, must send a reason, and the call writes an audit entry. A customer is refused. The seat goes from blocked back to free.

If he asks you to add it, show that path. If it is missing in the file he opened, copy the block path: check the role, require a reason, write the audit row, clear the block.

Say this

Release is an admin API with a reason and an audit row. A customer cannot call it. The seat becomes free.

Practice 5. Same checkout, tried twice

This already exists. If the order already has a payment, the second submit is a conflict. It does not insert a second payment and it does not call the mock again.

Say the limit out loud: this stops a second payment on the same order. It does not invent a new ticket. The seat rule is still the one active row.

Say this

A second checkout on an order that already has a payment is rejected. One payment, one mock call.

Practice 6. Two customers, last seat

Write a test, not a new rule. Two threads, two customers, one seat, real Postgres. One response is success. The other is conflict. After both finish, one active row exists. If both succeed, the partial index is not doing its job, or the test used a fake database.

Say this

I race two customers on one seat against Postgres. I expect one hold and one conflict, and a single active row at the end.

The habit for any live edit

  1. Say the rule in one sentence before you type.
  2. Change one place.
  3. Change the test at the exact edge.
  4. Run that test. If it fails, read the failure before you edit again.

Check

He wants confirmed tickets. Which count must you not reuse?

You change the half-refund edge from 48 hours to 24. What else must change?

The same checkout is submitted again after a payment row exists. What should happen?

Two threads hold the last seat on real Postgres. A correct test sees what?

Primary source for the habit of saying a test out loud: how would you test X. The code to point at is HoldSeats, RefundBand, and RecordPendingPayment.

Ask if you want to rehearse one practice by opening the real file together. Start with practice 2. It is the smallest edit.
