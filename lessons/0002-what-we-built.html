Lesson 2 · The build · about 10 minutes

What we built

Two programs share one database. The customer can book Harbor Lights in the browser. An admin does the rest by calling the API. There is no admin site.

Interview answers come after this picture is solid. The mission is still Sachin’s conversation. This lesson is the system you would be explaining.

The three pieces

  1. React siteport 5173 · the screens a customer sees
  2. Spring Boot APIport 8080 · every rule lives here
  3. PostgreSQLthe seats, holds, payments, and tickets

The site sends /api to the API. Flyway creates the tables. The tests call that same API against a real database, including two customers at once. The last full run in the README was 135 tests, all passing.

What a customer can do

  1. Sign inemail and password · caps apply to that account
  2. Searchby event name
  3. Open the seat mapsections, prices, free / held / blocked / ticket
  4. Hold seats10 minutes · or release the hold · or change seats
  5. Check outpick a mock result: success, decline, timeout, or unknown
  6. Open ticketscancel some or all · the refund uses the same four mock results

If every seat is taken, the map offers Join waitlist. When a seat frees, the next person gets a hold that lasts 15 minutes, and the map says it is held for them. The map reloads after that customer’s own action. It does not update by itself while the page sits open.

Example: Ada buys two seats

Starter data is one venue and one event. Harbor Hall has Orchestra seats A1–A12 and Balcony seats B1–B8. The event is Harbor Lights, 14 December 2026 at 8:00pm Eastern. The Standard tier is $50.00. Inside the early-bird window the price is $40.00. On 17 October 2026 that window is open, so the map shows $40.00.

Ada signs in, searches “Harbor Lights,” and opens the map. She selects Orchestra A1 and A2 and presses Hold seats. Those two seats are hers for 10 minutes. Grace cannot take them.

On the Hold screen she can attach one promo code, then Check out. She chooses the mock result success. The API writes the payment, then the tickets. A1 and A2 are no longer a hold. They are tickets on her order.

If she had chosen decline, she would have no ticket and the seats would be free again. If she had chosen unknown, the seats would stay held and the Check out screen would offer Reconcile payment. A later lookup of success writes the tickets without charging again.

What an admin can do

There is no admin website. An admin account calls the API. Each override needs a reason, and that call writes an audit entry. The overrides are: block a free seat, release a block, cancel the event, reschedule it, and issue an exceptional refund. An admin can also create an event, a price tier, and a promo code, and can read a small sales summary for one event.

Starter data already created Harbor Hall, the seats, Harbor Lights, and the Standard tier. Those setup screens were left out on purpose.

Left out on purpose

  • No screens for venue, section, seat, event, price tier, or promo code.
  • No sales chart. One API read returns the counts.
  • No live seat map. No real card charge. No tax.
  • No second promo code, and no percent-off promo.
  • No scheduler. Opening the event releases an expired hold that has no payment. A person finishes an unknown payment by reconciling it.
