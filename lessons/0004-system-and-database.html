7. Why PostgreSQL

We need three things a simple list in memory does not give us.

  • A unique rule that applies only to active rows. A released hold can stay in the table.
  • A row lock, so two requests can be forced to take turns.
  • A transaction, so a group of writes all stick or all undo.

The tests use that same Postgres database, not a fake one. A fake database would not prove the unique rule.

Say this

I picked Postgres because the “one active seat” rule is a partial unique index, and the tests run against that real database.

9 and 12. One seat, sold once

The index is named one_active_event_seat. It covers (event_id, seat_id) only where the row is active. A hold and a ticket are both active. A released hold is not, so it leaves the index and someone else can hold the seat later.

Two customers try the same seat at once. Both try to insert an active row. Postgres allows one. The other waits, then fails, and that request keeps no new hold.

A normal unique constraint would also block the old released rows. We need those rows to stay, so the index is partial: it ignores inactive rows. Postgres documents this shape in its partial-index examples.

Say this

Only one active hold or ticket can exist for a seat at an event. A released hold drops out of that index. The second customer’s insert fails.

10. What a transaction is

A transaction is a bundle of database writes. They all save, or they all undo. Nothing in the middle is visible as a finished fact.

We use one when we check the 6 and 12 caps and insert the holds. We use one when we save the pending payment. That payment transaction ends before the mock runs. Checkout itself is not one long transaction.

Say this

A transaction is all-or-nothing. I use one to save the holds, and one to save the payment. I end the payment transaction before I charge.

13. Crash between payment and the ticket

The payment row is already saved. The seat stays held. Opening the order, or a reconcile call, runs the lookup. Success writes the ticket and does not charge again. Decline frees the seat.

Say this

The crash leaves a saved payment and a held seat. A lookup finishes it. Success writes the ticket. Decline gives the seat back.

14. Why the lock is not held for 10 minutes

The 10 minutes are a timestamp on the saved hold, not a lock kept open. A lock lives only until the transaction ends. Holding one open while a person thinks would block other work, and the lock would vanish if the app died. The timestamp survives. Opening the event is what releases an expired hold that has no payment.

Say this

Ten minutes is a time on the row, not a lock I hold open. A lock that long would block everyone and die with the app.

15. Deadlocks

A deadlock is two requests each waiting for a lock the other holds. They never move. We lock seats in id order, lowest id first. If one request wants seats 2 and 9, and another wants 9 and 2, both lock 2 before 9. They take turns instead of waiting on each other.

Say this

I lock seats from the smallest id to the largest, so two bookings cannot grab the locks in opposite orders.
